# 0002. 定位为单角色个人学习工具

- 状态：Accepted
- 日期：2026-11-07
- 决策者：全员

## 背景

课题名称是"课程资料管理与错题复习系统"，第一反应会做成"教师建课传资料 + 学生选课做题"的双角色平台。但需求澄清后确认：**使用者只有学生本人**，是一个自学工具，不是教务系统。

这个选择影响极大：角色模型决定表数量、界面数量、权限复杂度。

## 决策

系统只保留 `STUDENT` 一种角色。课程 = 用户自建的学习空间；资料 = 用户自己收集的课件与网课；没有教师端、没有选课、没有班级、没有审核。

多账号可注册，但**数据严格按 `user_id` 隔离**，不存在任何跨用户可见的内容。

## 后果

**正面**

- 砍掉约 8~10 张表：教师-课程关系、选课、班级、作业、审核、通知已读……
- 权限模型从 RBAC 退化为"本人可见"，越权校验只需一个拦截器
- 界面从"教师端 + 学生端"变成一套界面，前端工作量减半
- 可以把省下的时间投入到真正有技术含量的部分：视频笔记、复习算法、统计

**负面**

- "课程资料管理"这半边的业务厚度变薄，容易被认为"只是个网盘"
  - 对冲手段：资料要做出**组织能力**（章节树、标签、预览、阅读进度），而不是只有上传下载
- 答辩可能被问"为什么没有教师端"
  - 答法：*"需求定位是个人学习工具，教师端会引入选课与权限体系，与本项目'复习闭环'的核心目标无关；我用视频笔记和复习统计把价值补在了使用深度上。"*
- 多人协作时少了"角色"这个天然的模块划分依据，要靠服务边界分工

## 备选方案

| 方案 | 为什么不选 |
|---|---|
| 教师 + 学生双角色 | 表、界面、权限全部翻倍，且与"复习"主线关系弱 |
| 加管理员做用户审核 | 单人自用场景，管理员没有存在意义 |
| 完全不做账号，本地单用户 | 失去 JWT/鉴权这一整块可讲的微服务内容，且无法演示数据隔离 |
