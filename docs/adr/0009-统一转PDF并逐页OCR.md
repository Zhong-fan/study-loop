# 0009. 统一转 PDF，逐页取文字，OCR 兜底

- 状态：Accepted
- 日期：2026-11-07
- 决策者：全员

## 背景

用户的真实动作是"把本地课件传上来，然后**在网页里读**"：翻页、找那一页、选中一句话、出题。这就要求文件必须能在浏览器里渲染。

但浏览器只能可靠渲染 PDF 与图片，不能直接渲染 doc/docx/ppt/pptx。而老师的课件恰恰大量是 PPTX。另一头，教学课件里存在大量**扫描件与图片型 PPT**——整页就是一张图，没有任何文本层，抽取结果为空。

两个问题合在一起，本质是同一个：**格式不统一、内容形态不统一**。

## 决策

**一条管线，所有格式收敛到"可渲染的页 + 每页的文字"：**

1. **统一转 PDF**：非 PDF 格式用 LibreOffice headless 转 PDF；PDF 直通。**原件永久保留，转换产物另存。**
2. **统一渲染**：前端一律用 pdf.js 按页渲染，PDF、PPT、Word、扫描件走同一套阅读器。
3. **文字层优先，逐页判定**：先用 PDFBox 抽该页文本；去空白后 < 20 字符，才判定为"无文字页"。
4. **OCR 兜底**：无文字页渲染成 PNG → 调云 OCR → 写回该页文字，标记 `text_source = OCR`。
5. **扫描页不做透明文字层**，改在右侧展示"本页文字"面板，供选中与出题。
6. **OCR 与 ASR 一致，走云 API**，抽象 `OcrProvider` 接口，未配置密钥时降级为"无文字"而不是报错。

## 后果

**正面**

- 一条管线覆盖所有格式，前端只有一种阅读器，后端只有一套页模型
- 扫描件从"只能看"变成"能搜、能选、能出题"，覆盖了真实课件的最大痛点
- 混合策略省钱：正常 PDF 一次 OCR 都不用，只有图片页才产生调用
- 页级处理互不影响：某一页 OCR 失败，整篇仍可用

**负面**

- **引入 LibreOffice 容器**（约 400MB），且**必须装中文字体**，否则转出来全是方块，整条管线废掉
- **页码口径变了**：DOCX 转 PDF 后分页由排版决定，Word 里"第 12 页"可能对应 PDF 第 13 页
  - 缓解：统一以 PDF 页码为准，界面注明"页码以预览为准"
- OCR 按次计费，扫描件页数多时成本不可忽略
  - 缓解：单文件 ≤ 300 页；只对无文字页调用
- 页图会发给第三方云服务，存在隐私与版权顾虑
  - 缓解：设置里提供总开关，默认开启并明确告知
- 转换是重 CPU 操作，大文件会拖慢服务
  - 缓解：独立线程池 + 子进程 + 超时熔断

## 备选方案

| 方案 | 为什么不选 |
|---|---|
| 只支持 PDF | 现实里最需要管理的恰恰是 PPTX；等于把用户挡在门外 |
| 前端直接渲染 docx（mammoth.js / docx-preview） | 只覆盖 docx，不支持 ppt，且排版与原文差异大 |
| 接 kkFileView | 它是完整的预览服务，会再引入一个容器和一套前端组件；我们只需要"转 PDF"，LibreOffice 更直接 |
| 本地 OCR（Tess4J / PaddleOCR） | Tess4J 中文准确率一般；PaddleOCR 要 Python 容器，与"V1 纯 Java"的目标冲突 |
| OCR 结果叠成透明文字层 | 需要逐字坐标对齐，错位后体验更差；面板方案更稳 |
