# 0003. 服务拆分：网关 + 三个业务服务

- 状态：Proposed
- 日期：2026-11-07
- 决策者：全员
- 修订记录：
  - v0.1 初版：网关 + auth / course / review
  - v0.2 增加 `media`（视频解析），曾改为四个业务服务
  - v0.3 **回退为三个**：视频延后，文档解析留在 `course`

## 背景

课程要求"采用微服务架构"。但每多一个服务就多一份配置、一个端口、一次联调、一个答辩时要解释的边界。拆错了就是分布式单体。

中途曾为"视频解析"拆出 `media` 服务，理由是负载特征差异（分钟级、CPU 密集、Python 运行时）。现在视频延后到 V3，而文档解析是**秒级、纯 Java 库调用**，没有拆的必要——为尚未发生的需求提前拆服务，是典型的过度设计。

## 决策

**1 个网关 + 3 个业务服务**，每个服务独占一个 schema：

| 服务 | 职责 | 独占 schema | 端口 |
|---|---|---|---|
| `gateway` | 路由、JWT 校验、CORS、登录限流 | — | 8080 |
| `auth` | 注册登录、令牌签发与吊销、个人设置 | `study_auth` | 8081 |
| `course` | 课程、章节、资料、**文档解析与页文本** | `study_course` | 8082 |
| `review` | 题库、判分、复习卡、组卷、统计 | `study_review` | 8083 |

拆分依据，按优先级：

1. **数据所有权**：一张表只能有一个服务写。
2. **变更频率**：改复习算法不碰资料解析，改预览不碰排期。
3. **负载特征**：*仅当差异达到数量级时才拆*。文档解析是百毫秒级，放 `course` 的独立线程池即可；视频转写是分钟级，才值得独立服务。

服务之间只传 id 与快照字段，不跨库 JOIN，不用分布式事务。

## 后果

**正面**

- 三个边界一句话能说清：谁管账号、谁管资料、谁管题和复习
- 部署只需 3 个 Java 进程 + 基础设施，单机扛得住
- 天然对应分工：鉴权 / 资料与解析 / 题库与复习

**负面**

- `course` 同时承担 CRUD 与解析，是一个偏重的服务
  - 缓解：解析走独立线程池（核心 2、队列 20），与 Web 线程隔离；超时 60 秒熔断
- 三个服务共享一个 MySQL 实例，属于逻辑隔离
  - 答法：*"课设规模下一实例多 schema 是成本与隔离性的平衡；换多实例只改连接串。"*
- 网关是单点
- **将来接视频时要再拆一次** `media`，属于可预期的返工
  - 缓解：`material` 表已预留 `source_type`，拆分时只影响解析链路，不动业务表

## 备选方案

| 方案 | 为什么不选 |
|---|---|
| 单体 + 模块化 | 不满足"微服务架构"硬性要求；但开发顺序仍先单体跑通再拆（M0） |
| 保留 4 个服务（含 media） | 当前 media 里只有一个秒级任务，纯粹增加部署与联调成本 |
| 按技术层拆（file / parse / stat） | 加一个功能要改三个服务，典型分布式单体 |
| 拆 5 个以上 | 团队 3~4 人，运维成本超过收益 |
