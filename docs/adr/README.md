# 架构决策记录（ADR）

> 这个目录记录**每一个"为什么这么设计"**。代码能说明"怎么做的"，只有 ADR 能说明"为什么不那么做"。

---

## 1. 为什么要有 ADR

课程设计里最常见的答辩事故：老师问"你为什么用微服务 / 为什么不用 MQ / 为什么算法用 SM-2"，学生答不上来，只能说"网上都这么写"。

ADR 的作用是把当时的权衡**当场记下来**，三个月后自己还能讲清楚。

## 2. 什么时候写

满足任意一条就写：

- 选了某个技术，同时放弃了另一个看起来更流行的
- 划定了服务边界、表边界、模块职责
- 定了一条会影响多人协作的约定（比如"所有删除都是软删"）
- 推翻了之前的决策（**必须**新写一条，不要改旧的）

不写：变量命名、包结构、某个接口的参数顺序。

## 3. 怎么写

- 文件名：`NNNN-短标题.md`，四位编号，中文短标题，全小写英文与连字符亦可
- 状态只有五种：`Proposed` 提议中 ｜ `Accepted` 已采纳 ｜ `Deferred` 暂缓 ｜ `Superseded by NNNN` 被取代 ｜ `Deprecated` 已弃用
- 一条决策一个文件，**写完不要改内容**，只改状态
- 正文控制在 60 行以内，写长了说明决策不够清楚

模板：

```markdown
# NNNN. 标题

- 状态：Proposed
- 日期：YYYY-MM-DD
- 决策者：姓名

## 背景
（遇到了什么问题，约束是什么）

## 决策
（我们决定做什么，一句话说清）

## 后果
- 正面：
- 负面：（必须写，没有负面说明没想清楚）

## 备选方案
| 方案 | 为什么不选 |
```
