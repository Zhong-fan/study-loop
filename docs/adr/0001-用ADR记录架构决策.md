# 0001. 用 ADR 记录架构决策

- 状态：Accepted
- 日期：2026-11-07
- 决策者：组长

## 背景

课程设计要答辩。代码能证明"做了什么"，但证明不了"为什么这么做"。常见的翻车场景：老师问"为什么拆成微服务而不是单体"，学生答"要求用微服务"；再问"为什么三个服务不是五个"，就答不上来了。

而且这类项目通常做 4~6 周，做决定的人和三个月后答辩的人，记忆已经不一样了。

## 决策

在 `docs/adr/` 下，用固定模板为每个影响架构的决定写一条记录；一条决策一个文件，只增不改，状态用 `Proposed / Accepted / Superseded / Deprecated` 四种。

## 后果

**正面**

- 答辩时每个"为什么"都有出处，且是当时写的，不是事后编的
- 新成员（或未来的自己）能快速理解约束，不会重复讨论已经定过的事
- 决策被推翻时留有痕迹，报告里"方案对比"一章可以直接摘

**负面**

- 每做一个决定要多花 10 分钟
- 容易写成流水账；必须靠"后果里必须写负面"这条强制思考

## 备选方案

| 方案 | 为什么不选 |
|---|---|
| 只在群里讨论 | 聊天记录会丢，且无法引用 |
| 写一份大而全的《设计文档》 | 一次写几千字，最后没人读；决策点埋在里面找不到 |
| 写在代码注释里 | 只对改这个文件的人可见，且重构时会丢 |
