# 0008. 先做文档解析，视频解析延后

- 状态：Accepted
- 日期：2026-11-07
- 决策者：全员

## 背景

v0.2 把"视频解析（字幕 / ASR / 时间戳）"当成了核心能力，并为此拆出 `media` 服务、引入 Python 侧车。但冷静下来看，这条路有三个成本：

- 运行时异构：yt-dlp / ffmpeg / whisper 都要装，镜像大、环境易碎
- 时间成本：40 分钟音频要转 5~10 分钟，演示时无法即时反馈
- 效果不稳：平台反爬、无字幕、识别错字，任何一个都能让演示翻车

而课程设计的**真正目标**是"资料 → 出题 → 复习"的闭环。这个闭环完全可以用 PPT / PDF 实现，且成本低一个数量级：文本本来就在文件里，PDFBox / POI 直接读，秒级完成。

## 决策

1. **本期聚焦文档**：PDF / PPTX / DOCX 的文本抽取、按页（幻灯片）定位、全文检索、选中出题。
2. **视频整体延后到 V3**，不在 V1/V2 范围；[ADR-0006](0006-视频解析用ytdlp加本地whisper.md) 状态置为 `Deferred`，设计保留。
3. **遗留决策（等做视频时执行）**：语音转写走**云 API**，不自建 Whisper 容器。理由：省掉模型与环境维护，识别质量更高；代价是需要账号与费用、演示环境要联网。届时需把 provider 抽象成接口（阿里云 / 腾讯云 / OpenAI 兼容），配置切换。
4. `material` 表预留 `source_type`（FILE / VIDEO）与 `source_url`，将来接入视频不改表结构。

## 后果

**正面**

- V1 的全部依赖都是纯 Java 库，`docker compose` 起来就能跑，无外部账号、无模型文件
- 解析秒级完成，操作有即时反馈，演示节奏可控
- 页码定位比时间戳更准：用户说"第 12 页"，系统记的就是第 12 页
- 服务数从 4 降回 3，少一套部署与联调

**负面**

- **扫描版 PDF / 图片型 PPT 抽不到文字**，这部分资料只能预览、不能检索
  - 这是本决策最大的代价，必须在报告里作为"已知限制"写明
- "视频笔记"这个亮点被推迟，V1/V2 的演示少了一个视觉冲击点
  - 对冲：用"划选文本立即出题 + 复习时跳回原文"替代，效果同样直观
- 将来真做视频时，云 ASR 会产生费用，且要处理密钥管理与超时重试

## 备选方案

| 方案 | 为什么不选 |
|---|---|
| 先做视频，文档后置 | 视频链路的外部依赖最多，最容易卡住整体进度 |
| 两者并行 | 3~4 人团队同时开两条解析链路，等于两条都做不完 |
| 文档 + 本地 Whisper 都做 | 仍是异构运行时问题，且本地模型演示慢 |
| 完全砍掉视频 | 需求里明确要，且技术方案已论证可行，只是排期问题 |
