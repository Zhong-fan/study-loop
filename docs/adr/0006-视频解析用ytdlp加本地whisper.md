# 0006. 视频解析用 yt-dlp 统一入口 + 本地 Whisper

- 状态：**Deferred（暂缓，见 [0008](0008-先做文档解析视频延后.md)）**
- 日期：2026-11-07
- 决策者：全员

> 本条暂缓执行：视频解析被排到 V3，本期先做文档解析。将来恢复时需按 ADR-0008 的遗留结论调整——**ASR 改走云 API**，不再自建 Whisper 容器；yt-dlp 统一入口的思路保持不变。

## 背景

需求确认：视频的价值不是"能播"，而是**能变成可检索、可出题的文本**。同时来源不能限定 B 站——老师发的录屏、YouTube、其他平台的公开课都要能进来。

要在"支持很多平台"和"代码量可控"之间找平衡。逐平台写解析器是最差的选择：每个平台的接口、签名、反爬都不同，维护成本会吃掉整个项目。

## 决策

1. **统一入口 yt-dlp**：不写平台专属解析器，用户给链接或文件，全部交给 yt-dlp 取元数据与音轨。它支持上千个站点，B 站、YouTube 都是内置 extractor。
2. **字幕优先，ASR 兜底**：有字幕直接取（人工 > 自动），没有则抽音轨走 `faster-whisper` 转写。
3. **音频是临时文件**：转写完成立即删除，只持久化段落文本。不存储视频、不提供下载、不二次分发。
4. **独立 `media` 服务 + Python 侧车**：Java 只做编排（建任务、轮询状态、落段落），Python 侧车做取流与推理，两者 HTTP 通信。
5. **异步任务 + 轮询**：提交返回 `taskId`，前端每 2 秒查一次状态，不占用长连接。

## 后果

**正面**

- 一处适配，多平台可用；新增平台通常只需升级 yt-dlp 版本
- 完全离线可演示，不依赖任何云服务账号
- 解析失败不影响其他功能，任务可重试
- 段落文本落库后，搜索、出题、统计全部变成普通 SQL

**负面**

- 团队要维护一个 Python 容器，且模型文件让镜像变大（`small` 约 500MB，加 `int8` 量化可控）
- CPU 转写慢：40 分钟音频约 5~10 分钟，演示前需提前跑好
- yt-dlp 会被平台反爬影响，需要定期升级版本
- **合规边界必须讲清楚**：只处理用户有权访问的内容，音轨仅本地转写后删除

## 备选方案

| 方案 | 为什么不选 |
|---|---|
| 每个平台写一个解析器 | 维护成本爆炸，且答辩时会被问"为什么只支持这两个" |
| 云 ASR（讯飞/阿里） | 快且准，但要账号、要计费、现场网络不可控 |
| 只用平台字幕，不做 ASR | 大部分课程视频没有字幕，功能等于废掉一半 |
| 浏览器端 Web Speech API | 中文识别质量差、需联网、无法处理长音频 |
| 大模型直接总结视频 | 成本高、不可解释，且与"出题/复习"主线关系弱 |
