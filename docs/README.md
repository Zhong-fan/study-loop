## 3. 写作规则

1. **单一事实来源**：同一件事只在一个文件里定义，其他地方用链接引用，不复制粘贴。
2. **版本化**：需求类文档带版本号（`v0.1`），改动时在文件头加变更记录，不覆盖历史。
3. **ADR 只增不改**：决策变了就新写一条，标注 `Supersedes NNNN`，旧的那条改成 `Superseded by NNNN`。
4. **废弃即归档**：被取代的文档移到 `archive/`，文件名加日期和后缀，文首加废弃说明。
5. **不写"待补"超过一周**：写了待补的事项，要么本周补上，要么删掉。
6. **图优先**：能用一张图说清的，不要写三段话。图用 Mermaid，跟着代码一起 review。
7. **中文为主，字段名保留英文**：`review_card`、`ease_factor` 这类直接写英文，不翻译，避免同一概念两种叫法。

## 4. 谁维护

| 文档 | 负责人 | 兜底 |
|---|---|---|
| 需求规格 | 组长 | 全员可提 PR |
| ADR | 提出该决策的人 | 组长 |
| 数据库 / 接口 | 对应模块负责人 | 组长 |
| README / CHANGELOG | 组长 | — |

> 组长不是"写文档的人"，是"保证文档不烂的人"。每周五花 10 分钟扫一遍 `git log -- docs/`，看有没有改了代码没改文档的。

## 5. 答辩前检查

- [ ] README 的"当前状态"已更新到真实进度
- [ ] 所有 ADR 状态正确（没有长期 `Proposed` 的）
- [ ] `archive/` 里没有仍在被引用的文档
- [ ] 需求规格里的验收脚本，逐条能演示
- [ ] 没有文档描述的功能在系统里不存在（**这条最致命**，老师会照着文档点）
